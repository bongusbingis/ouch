# Splat Brawl (ouch)

Roblox PvP arena brawler: dodgeball (ranged) vs. inflatable hammer (melee), FFA and TDM in one permanent Studio-authored arena. The design source of truth is `docs/Splat_Brawl_GDD.md`; `docs/dodgeball-studio-setup.md` covers manual Studio-side asset setup.

## Hard rules — read before writing any code

1. **No excessive commentary.** Inline comments are for constraints and invariants that cannot be understood by reading the code — nothing else. No comments narrating what a line does, no "changed X to Y" commentary, no section banners. Match the existing style: a short block comment at the top of a module stating its responsibility and invariants, then near-zero inline comments.

2. **Never use `:FindFirstChild()` for Studio-authored assets that must exist at runtime** (sounds, animations, templates, map folders, UI views, etc.). Use `:WaitForChild()` — if the asset is missing, the infinite-yield warning / error is the *correct* behavior and surfaces the setup problem. `FindFirstChild` silently hides missing assets. `FindFirstChild` is acceptable only for things that legitimately may not exist (e.g. `character:FindFirstChild("HumanoidRootPart")` during death/streaming, optional runtime state). Follow the existing pattern: `WaitForChild` then `assert(x:IsA(...), "[Service] path must be a T")`.

3. **Never use `Instance.new()` to create gameplay assets** — no imperative UI screens, buttons, effects, or sounds unless specifically directed. Both places render UI through React components under `src/shared/UI` and their place-specific client trees; reuse those components and the existing React roots. If a needed Studio asset does not exist yet, **tell the user exactly where it should live in the hierarchy and what properties/children it needs** (as `docs/dodgeball-studio-setup.md` does), or ask how they want it structured. `Instance.new` is fine for non-gameplay infrastructure (organizational Folders, RemoteEvents/Functions, `InputContext`/`InputAction`/`InputBinding`, physics constraints for ragdolls, invisible markers/waypoints) and for cosmetic visual construction (`CosmeticVisualFactory` clones an authored template MeshPart and applies code-defined config on top — see the Cosmetics section below).

4. **One source of truth per piece of state; simple, single-responsibility modules.** This codebase is built around explicit single-owner state and the doc comments name the owner (e.g. ball possession lives *only* in `ProjectileState.phase/heldBy`; alive/dead lives *only* in the `CombatAlive` attribute; profile `Cosmetics.*` is written *only* by CosmeticsService). Never introduce a second copy of state that can drift, race, or mismatch — derive, don't duplicate. Keep functions small and pure where possible, push side effects to the owning service, and handle edge cases (player leaves mid-match, character missing, profile not yet loaded, duplicate events, latency) deliberately — existing code dedupes events, uses generation counters to cancel stale timers, and pcalls listener dispatch for a reason.

5. **Make zero architectural guesses.** If the plan, scope, or prompt leaves an architectural decision open (where state lives, which layer owns a behavior, hierarchy of a new Studio asset, a new remote's shape), do not pick one silently — ask the user what the intention or decision should be. Guessing is only acceptable when the user has specifically directed it.

Also: **never author or edit the contents of a place `.rbxl` with repository tooling.** They are Git LFS binaries authored only in Studio. The single tool that writes them is `pull-places.sh`, which replaces a file wholesale with what Roblox currently has published; the deploy pipeline only ever reads them, merging the rojo build into a copy.

## Toolchain & commands

Tools are pinned in `rokit.toml` (rojo, wally, lune, stylua, selene, rbxcloud). Run `rokit install` and all commands from the repo root.

```sh
wally install                                      # populate Packages/ (gitignored)
lune run src/scripts/lune/run-tests.luau           # run all specs headlessly (regenerates sourcemap.json via rojo)
bash src/scripts/shell/lint.sh src                 # selene lint shared code
bash src/scripts/shell/lint.sh places/arena        # selene lint arena code
bash src/scripts/shell/lint.sh places/lobby        # selene lint lobby code
bash src/scripts/shell/check-format.sh src
bash src/scripts/shell/check-format.sh places/arena
bash src/scripts/shell/check-format.sh places/lobby

ROBLOX_API_KEY=... bash src/scripts/shell/pull-places.sh          # import both live places
ROBLOX_API_KEY=... bash src/scripts/shell/pull-places.sh arena    # or just one
```

CI (`.github/workflows/cicd.yml`) runs lint, format checks, Lune tests, deployment-tool regressions, and both complete place builds on every PR to `main`/`prod` and every push to either branch. Each build merges Rojo output into a copy of the committed Studio-authored base under `places/<place>/`, validates the input, and retains the merged artifact with its commit and SHA-256 provenance. Only a push to `prod` can publish. Complete production runs share a non-canceling queue; one release job verifies its artifacts, uploads and tests a Saved version for every affected place, then publishes those same bytes only after all suites pass. `places/<place>/**` and its project select that place; shared code, dependencies, toolchain, and CI changes select both. Both places need an in-place suite: shared harness in `src/tests/` (`Runner`, `Helpers`), place-specific specs in `places/<place>/tests/`. Planning errors and empty suites fail publication. See `docs/cicd.md` for artifact contracts and failure recovery.

## Systems

### Deterministic combat sim — `src/shared/Game/Sim/`

`SimCore.step` is a pure fixed-tick function run by the authoritative server. It owns no engine state: characters and geometry arrive in a `WorldSnapshot`, time is the tick counter, results leave as mutated `SimState` plus an ordered `SimEvent` list.

- **Determinism rules:** no `Instance` access, no wall clock, no unordered iteration — always `SimUtil.sortedKeys` over keyed tables. Predicates shared across weapons and projectiles (`sameTeam`, `hasLineOfSight`, `hasHandBall`, `pushEvent`) live in `SimUtil` so every module applies identical rules — don't re-implement them locally. Input commands are canonically sorted so server resimulation agrees with the predicting client regardless of arrival order.
- **Weapons** implement the `WeaponKit` interface (`kind`, `commands` routing set, `init`, `handleInput`, `tickPlayer`, optional `tickWorld`) and register in `WeaponRegistry`. Adding a weapon = one kit module + one registry entry; sim core, adapter, and netcode do not change.
- `Weapons/Dodgeball.luau`: ball possession has exactly one source of truth — `ProjectileState` (`phase == "Held"` + `heldBy`). Kit state holds cooldowns plus the transient catch window and direction; it never duplicates possession. Aim assist / homing parameters come from `Config.Gameplay.AimAssist`, keyed by device class (Mouse/Touch).
- `Weapons/Hammer.luau`: kit state is a small phase machine (cooldown → active dash → recovery). The recovery window is the GDD's whiff-punish mechanic — do not remove it.
- `Projectiles.luau`: generic swept-projectile subsystem — fixed-tick kinematics, homing steering, swept-sphere vs. capsules and static AABBs, substepped (max 8) to prevent tunneling. Projectile phases: `Held | Windup | InFlight | Bouncing | Rolling | Free`. Archetype params live in `Config.Gameplay.Combat`.
- `MatchSim.luau`: pure match phase machine (`Idle → Starting → Active → Results → Intermission`) parameterized by the active mode's `MatchRules`; it decides scores and match flow only. Consequences such as respawns and arena teleports are applied by MatchService.

### Netcode / adapters — `src/shared/Game/Adapters/`

`ServerAuthAdapter` is the single bridge between the sim and the engine, and runs **server-side only**: a fixed 60Hz accumulator on `Heartbeat` decodes `SimState` from the ball instances, turns queued client intents into sim commands, runs `SimCore.step`, and encodes back. Clients send throw/catch intent over `SubmitCombatInput` and nothing else; the aim origin is taken from the player's own root on the server, never from the client. Resulting events are broadcast over the unreliable `CombatSimEvent` remote for presentation only.

Weapon animations are started by the acting player's own client (`WeaponAnimations`, fed by `CombatInputSender.onIntent`) so they are not delayed by a round trip; playback on the local character replicates outward and stays the only copy. The server must not also play them, or they restart on the actor. Which weapon a `Throw` press belongs to is **chosen, not derived**: `PlayerCombatState.equipped` is the single source of truth, encoded onto the character by `SimStateCodec` (`SimStateCodec.EquippedAttribute`) like every other piece of sim state, and read from there by the HUD and `WeaponAnimations` — there is no second copy kept for the client. Anything the codec does not carry is reset one tick after it is set, because the adapter decodes a fresh state every step. The routing rule is one line — a command claimed by several kits goes to the equipped one, a command only one kit claims (`Catch`) always routes — so no weapon is special-cased. Gaining a ball auto-equips the kit that declares `equipOnHandBall`, which is what keeps picking one up enough to throw it. Clients switch over `SubmitWeaponEquip`; equips are applied in their own pass so they never consume the one action a player gets per tick.

`PlayerIds` is the single owner of the sim player-id convention (UserId as string): every translation between a `Player` and a sim/event id goes through `toId`/`fromId`/`fromEvent` — never `tostring(player.UserId)` inline. `EventDedup` is the shared dedup guard for sim/match event consumers (`EventDedup.new(cap?)` → `markSeen(event)`/`clear()`); every event consumer that must not double-apply a side effect uses it instead of a hand-rolled seen-table.

`SimStateCodec`: attributes on the ball instances are the between-tick source of truth and replicate to clients for presentation. Attribute names are deliberately short (`ph`, `hb`, `ow`, `er`, `ft`, `vel`) because of replication limits (first 64 attributes, ≤50-char names). Ball position is *not* an attribute — it lives in the part's CFrame, set by the server each tick and replicated natively; `BallVisuals` smooths it with `Combat.Dodgeball.RemoteSmoothing`.

**Security invariant (GDD §8):** hits, catches, eliminations, and respawn timing are server-authoritative. Clients send inputs and render feedback; never trust client raycasts or client-reported hits.

### Match orchestration — `src/server/Modules/`

- **MatchService** (the largest service) drives `MatchSim` with the selected mode's rules and owns the match lifecycle: arena teleports, ball provisioning via mode hooks, elimination consequences, and respawn scheduling. Only ModeVoteService (plus explicit developer/test tooling) calls its server-only `beginMode(modeId)` seam. Replicated UI surface: `ReplicatedStorage.MatchState` folder attributes (`phase`, `timeRemaining`, `winnerId`, `modeId`), per-player `MatchScore` attribute, leaderstats `Elims`, and `MatchService.onEvent` for killfeed-style consumers. Respawns use per-player generation counters so a new death/leave cancels a stale scheduled respawn; TDM uses synchronized wave respawns (`WaveRespawnSeconds`).
- **ModeVoteService**: sole owner of the 10-second authoritative ballot, deadline, counts, late-ready extension, and random tie/no-vote resolution. `ArenaSessionService` releases its 20-second readiness gate when all expected clients are ready or the deadline passes with at least one ready client; it never opens an invisible zero-ready vote. The service projects coherent snapshots through `ReplicatedStorage.ModeVoteState`, projects each accepted selection through the player's `ModeVoteSelection` attribute, and accepts only admitted, ready players and validated mode IDs over `SubmitModeVote`. `ModeOptions` canonicalizes version-skewed lobby options and falls back to the current enabled ballot if none survive. The React UI derives from those projections and never updates optimistically.
- **Modes** (`src/shared/Game/Modes/`) implement `GameMode` (`MatchRules` + server-only hooks receiving only ball provisioning, player, and team levers). `MatchRules.PreserveDodgeballs` (true for every shipped mode) sends a ball that comes to rest back to whoever last owned it instead of leaving it as a world pickup; a catch reassigns `ownerId`, so a caught ball is a transfer and returns to its catcher from then on. The sim reads this as data through `WorldSnapshot.rules`, which `ServerAuthAdapter` resolves from the replicated `modeId` — the sim still never names a mode. Registered in `ModeRegistry` (FFA, TDM, Infection). Infection converts on elimination rather than scoring: `ModeContext` carries `setPlayerTeam`, `getPlayerById`, and `finishMatch` for it, and `MatchRules.TimeCapWinnerId` lets a mode declare that surviving to the clock is itself the win instead of the leading score deciding. Side asymmetry is still carried by ball possession alone: infected never receive a ball, so their dodgeball slot has nothing in it and every attack they make is the hammer. Survivors, since weapons became a choice, can equip the hammer while holding a ball — the asymmetry is now "who has ammunition", not "who swings". No weapon code is mode-aware either way. `PartyTeamAllocator` keeps lobby parties together while minimizing TDM imbalance. Rules are shared modules so tests and client UI can read them.
- **EliminationService**: the `CombatAlive` character attribute is the single source of truth for alive/dead (nil/true = alive, false = eliminated). It never touches native Humanoid health or `LoadCharacter`. Also owns the ragdoll (BallSocket constraints with per-joint limits) and restore.
- **BallService**: the *sole* creator of ball instances — constructs the default template via `CosmeticVisualFactory.create("BallAssets", nil)` and clones it into `Workspace.Balls`. Match modes grant one persistent held ball per entrant. Provisioning is outside the deterministic sim (not input-driven); balls join the sim as replicated instances.
- **ArenaService**: validates the permanent Studio-authored `Workspace.Assets.Arena` with `Map`, `Scriptables`, `PlayerSpawns`, and `TeamSpawns.Red`/`Blue`. It caches direct-child spawn parts and teleports players without cloning, reparenting, or destroying arena content.
- **ArenaSessionService**: validates lobby TeleportData and its authenticated source place/universe when players arrive, then owns the arena server's immutable matchmaking-session identity, admission state, and party identity. Party identity survives a disconnect for same-server reconnection; malformed, untrusted, or mismatched arrivals are excluded from voting and gameplay. It also owns client readiness: `ArenaClientReady` is accepted only after profile load and the client loading gate completes, then projected as the `ArenaReady` player attribute. Direct joins remain valid but do not invent session state.
- **ArenaReturnService**: at `MatchReset`, once the results screen has played, returns lobby-originated players to `Env.LobbyPlaceId` grouped one teleport per party, carrying a `ReturnPayload` (party id, match id, member user ids). The decision is **per player**: a player with a party identity goes back, while a direct join is left alone. The shared retry coordinator retries transient failures and exposes Retry/Stay after final failure. The lobby accepts return payloads only from the configured arena in the same universe, atomically restores a surviving `Teleporting` party to `Lobby`, and otherwise regroups on whichever member arrived first.
- **MovementSpeedService**: the *sole* writer of `Humanoid.WalkSpeed` — named multiplicative modifiers (`setModifier`/`clearModifier`/`applyTimedModifier`) compose over a captured base speed; never set WalkSpeed directly elsewhere.
- **MapFeatureService**: drives the authored features under `Workspace.Assets.Arena.Scriptables` from one Heartbeat. Each kit in `places/arena/server/Modules/MapFeatures/` owns one folder there and implements `MapFeatureKit` (`folderName`, optional `tickPlayer`/`tickWorld`/`forget`), registered in `MapFeatureRegistry` — adding a feature is one module plus one registry entry, mirroring `WeaponKit`/`WeaponRegistry`. Shipped kits: `ElimZones` (immediate elimination via the `MatchService.eliminate` seam, so scoring/feed/respawn stay in one place), `JumpPads` (trampolines: authored Models rather than BaseParts, launched on a jump taken from the pad or a fast fall onto it, with a VectorForce cancelling part of gravity for the floaty arc and a broadcast impulse driving the client squash), `FoamPits` (slow via a MovementSpeedService modifier). Membership is a volume test on the root (`src/shared/Game/MapFeatures/Volume.luau`, spec-tested), not a touch trigger, and folders are re-read on change so parts can move or spawn at runtime.
- **RotatingPlatforms** (`src/shared/Game/MapFeatures/`) spins the assemblies under `Scriptables.Rotating`. Each assembly is a folder holding an `Origin` BasePart (the axis) and an `Assembly` Model that turns about Origin's up axis. It is deliberately *not* a MapFeatureKit: clients need the registry even though only the server moves anything. `startMover` is server-only and clients call `load` — two sides writing the same anchored assembly fight each other, which reads as violent stutter rather than rotation. The pose is a pure function of `Workspace:GetServerTimeNow()` (`Rotation.angleAt`, spec-tested) rather than accumulated frame deltas, so it never drifts. `PlatformRider` (client) carries the local character with the platform it rides, including while airborne over its footprint so a jump lands in the same relative spot; position only, never facing. It measures the delta from the assembly's own pose frame over frame, so replication lag cannot desync the carry from what the player is standing on.
- **InputSetup**: materializes the declarative map in `Config.Interface.Input` as an `InputContext`/`InputAction`/`InputBinding` tree under each Player (contexts must be Player descendants for engine ownership/replication). Owns the validated `DeviceClass` attribute the adapter stamps onto commands.

### Data & economy — `src/server/Modules/`

- **PlayerData**: ProfileStore profiles (template in `Config.Progression.Data`, store key in `src/server/Env.luau`) replicated to the owning client via Replica (token `"GameProfile"`). Exposes a write-through proxy so mutations replicate automatically; go through PlayerData's API (`get`, `addBonks`, progression deltas), never a second cache of profile data.
- **ProgressionService**: accumulates per-match progress (elims, deaths, catches, wins, XP, bonks) from match events — with event dedup — and commits via PlayerData. XP/Bonks award values live in `Config.Progression.Data`.
- **QuestService**: server owner of quest state (stored in the profile under `Quests`, daily reset key). Consumes match/sim events with dedup keys; pure rules live in `src/shared/Game/Quests/QuestLogic.luau`. Remotes: `GetQuestState`, `ClaimQuest`, `QuestStateChanged`. Rewards granted through **RewardService** (currently Bonks only).
- **CosmeticsService**: the *only* writer of profile `Cosmetics.*`. The profile is the source of truth; `Equip_<Slot>` player attributes are a read-only projection so every client can render other players' equips.
- **ShopService**: sole owner of `profile.Shop` — the rotating shop's drawn offers and the period they were drawn for. The draw itself is pure (`ShopRotation`, deterministic from userId + period index), but the *result* is stored, because the draw excludes owned items and recomputing after a purchase would reshuffle the offers the player chose not to buy. `ShopRotation.pool()` structurally excludes Exclusive items (`Rarity ~= "Exclusive"`) and respects the per-item `ShopEligible` flag (`nil` = category default, `true` = opt-in, `false` = opt-out). Items in a rotation category are purchasable only while offered, which `DirectPurchaseService` enforces through `ShopService.isPurchasable`. Bucketing for all three schedules (rotating shop, featured crate, featured bundle) goes through `FeaturedRotation.periodIndex`. Shop A/B levers are live-overridable and labelled by `Shop.VariantId`, which is stamped on every shop analytics row; see `docs/shop-economy.md`. The shared `EconomyService` starts the same service cohort in both lobby and arena.
- **CrateService**: two purchase paths — Bonks via the `OpenCrate` remote, Robux via MonetizationService receipts — sharing one roll-and-grant routine; every open fires `CrateOpened`. The roll itself is pure (`src/shared/Game/Economy/CrateRolls.luau`, injected `Random`) so tests pin distributions and the dupe-refund rule. Active crates: DodgeballCrate (BallAssets), HammerCrate (HammerAssets), EffectsCrate (TrailAssets + ElimEffectAssets + ImpactEffectAssets). `Crates.poolOf()` auto-derives pools from `Cosmetics.Items`, structurally excluding Exclusive items.
- **MonetizationService**: owns `ProcessReceipt`. Receipts are recorded in the profile for idempotency (retry after grant returns `PurchaseGranted` without re-granting); unknown products/failures return `NotProcessedYet` so Roblox retries. New product types register a handler in its `handlers` table.

**No competitive advantage:** nothing purchasable may affect combat outcomes — no weapon, movement, damage, cooldown, or health value is ever for sale (GDD §2, §7). Progression boosters (XP/Bonks multipliers) are permitted and live in `GamePasses.Boosts`; they change earn *rate* only. If a proposed offer would change who wins a fight, it is out of scope regardless of how it is framed.

### Cosmetics — `src/config/Cosmetics/` + `src/shared/Game/Cosmetics/`

**Catalog** (`Cosmetics.luau`): central cosmetic config exporting types, `Rarities` (Common/Rare/Legendary/Exclusive with crate weights), `Slots`, `VisualFolders`, `Defaults`, `Items`, and `VisualTemplates`. Items are split across sub-modules (`DodgeballItems.luau`, `HammerItems.luau`) merged into `Items` at load time with duplicate-key assertions. Each item is keyed by a string ID (`DodgeBall1`, `Hammer12`, etc.) stored in the player profile; changing it after launch requires data migration.

**Visual construction** (`CosmeticVisualFactory.luau`): the single shared path for building cosmetic visuals. **Neither `MeshPart.MeshId` nor a `SurfaceAppearance`'s PBR maps can be written from a runtime script** (they need Plugin capability), so a cosmetic visual can only ever be an authored MeshPart that is cloned — never one built from config. `create(category, itemId)`:
1. Resolves the item (or category default) definition
2. Clones the authored part — `Assets.Cosmetics.Templates.<Template>` for a category default, or `Assets.Cosmetics.<VisualFolders[category]>.<ItemId>` for an item. Its mesh, SurfaceAppearance, and any effect children (ParticleEmitters, Trails) all come along with the clone
3. Applies the `VisualDef` → `VisualTemplateDef` cascade for the properties that *are* writable: Size, Color, Material

Because the mesh and its maps are authored, config and the asset are two records of one thing. `MeshId` and `SurfaceMaps` stay in config as the record of what each authored part must carry, and the arena in-place asset spec is what holds the two in agreement — it asserts every item has a correctly-named MeshPart with the declared mesh and PBR maps. Without it a mis-imported or misnamed part renders the wrong skin with nothing failing.

Callers: BallService (server, default template), BallVisuals (client, per-owner equipped ball), HammerVisuals (client, per-player equipped hammer), WeaponViewport (UI preview), InventoryPreview (UI preview), PartyCharacterRenderer (lobby).

**Templates** (`VisualTemplateDef`): `MeshId: number`, `Size: Vector3`, `Color: Color3`, `Material: Enum.Material`, optional `SurfaceMaps: SurfaceMaps?`. A template describes the *category default* only. Every entry needs a matching MeshPart under `Assets.Cosmetics.Templates`; the Dodgeball template carries the ball's effect children, the Hammer template its SurfaceAppearance.

**Items** (`VisualDef`): `Template: string` (which template's Size/Color/Material to fall back on) plus per-item overrides. Common dodgeballs override `Color` only; PBR dodgeballs and all hammers declare `SurfaceMaps`. **Adding an item is an authored asset plus a catalog entry**: a MeshPart named exactly the item ID under the category's `VisualFolders` folder, carrying the mesh and SurfaceAppearance the entry declares. `VisualFolders` maps a category to that folder (`BallAssets` → `DodgeBalls`, `HammerAssets` → `InflatableHammers`); a category absent from it has no per-item mesh.

**Acquisition guards**: Exclusive items (Weight=0) are structurally excluded from both crate pools (`poolOf()`) and shop rotation (`ShopRotation.pool()`). The per-item `ShopEligible: boolean?` flag controls shop rotation eligibility independently (`nil` = category default, `true` = opt-in even if category is not drawn, `false` = opt-out even if it is). Exclusive exclusion takes precedence over ShopEligible.

**HammerGrip** (`HammerGrip.luau`): pure function that finds the longest axis of a hammer's Size for grip positioning. All shipped hammers share the same Size, so the grip solution is uniform; a future different-mesh hammer gets its own solution automatically.

### Client — `places/arena/client/Modules/`

- **Input/**: `InputRouter` feeds `AimDirector`'s aim into the `Aim` InputAction every frame, pulses `Throw` on touch taps, and reports mouse, touch, or gamepad device class. It releases the centered mouse only while the authoritative mode vote is open. `AimDirector` owns aim/soft-lock target selection.
- **Presentation/** (BallVisuals, HammerVisuals, DamageFeedback, DeathEffects, WorldAudio; CharacterRig owns rig-name lookups like the R15/R6 right-hand fallback): rendering and audio feedback *only* — they react to sim events, attributes, and remotes and hold no gameplay authority. BallVisuals and HammerVisuals call `CosmeticVisualFactory.create()` to build per-player cosmetic visuals (MeshParts with SurfaceAppearance) from the equipped item's config. Gameplay effects (trails, emitters) come along with the template clone and are enabled/disabled by phase; broadcast events can arrive more than once, so effects must deduplicate (test at 0/100/150/200 ms latency per `docs/dodgeball-studio-setup.md`).
- **UI/**: every arena UI is React; there is no imperative or Studio-authored UI left in this place. `ArenaApp` is the arena React root and renders the shared `GameModeSelect` from `ModeVoteClient`'s derived replicated snapshot. Presentational components never require Network or own gameplay state; client-to-server actions stay in the arena adapter. Shared interaction, responsive text, feedback, and motion primitives live under `src/shared/UI`.

### Networking — `src/shared/Network.luau`

The single place remotes are declared: add to its `definitions` table (name → `"event" | "function" | "unreliable"`) instead of creating ad-hoc RemoteEvents. Server handlers get per-player rate limiting via `checkRateLimit` — keep limits on any new client-invokable remote.

**Gameplay audio.** `Config.Infra.Audio.Gameplay` names each one-shot with a list of `AssetIds` (picked from at random, so a single-element list is a sound with no variance), a `Volume`, and a `Scope`. `GameAudio` (arena client) is the only caller: `World` scope spawns an `AudioPlayer` wired to an `AudioEmitter` on the event's host instance (or a throwaway anchor for a bare position), `Local` scope routes to `ClientAudio.play` for a flat 2D cue. Switching an effect between the two, or adding variance, is a config change. `GameAudio.onEvent` owns which sound belongs to which sim event, including distinguishing the three `Elim` variants — a projectile means dodgeball, a source without one means hammer, neither means an elimination zone. The older Studio-authored `SoundService.CombatAudio` templates still serve the sounds with no config ids (`Windup`, `Pickup`, `Landing`, `Hit`, `Miss`).

### Config — `src/config/`

All tunables live here and nowhere else: combat feel (`Combat`, cmdr-tunable at runtime; units are studs/seconds/degrees), aim assist per device class (`AimAssist`), input map (`Input`), game-mode vote metadata/timing (`GameModes`), arena features (`MapFeatures`, pending the `Scriptables` pass), data template + XP/Bonks tables (`Data`), quests, cosmetics, crates, products, UI, debug flags. New gameplay constants go in the matching config module, not inline.

**Live configs (`LiveConfig` + `ConfigLiveService`).** `src/config/LiveConfig.luau` is the allowlist of leaves that Roblox experience configs (`ConfigService`) may override at runtime; a leaf not declared there can never be changed live. `ConfigLiveService` (server, both places) reads the snapshot, validates every value against the declared type and range, and installs it by writing into the config table consumers already read — there is no second resolved copy to drift from it. The baked value of each leaf is captured on first override and restored exactly when the override disappears, so **the game always falls back to the values in `src/config`** when the config APIs fail, and a resync is all-or-nothing so a partial read cannot install a half-applied set. `ConfigSnapshot.UpdateAvailable` drives refreshes, with a periodic resync as a safety net.

`ConfigService` is server-only, so the active set is mirrored to clients through `ReplicatedStorage.ConfigState` (one value object per active override, named with underscores, plus a `revision` attribute bumped last as the commit signal as `ModeVoteState` does; value objects rather than attributes because replication caps an instance's total attribute payload at 1024 bytes) and re-validated client-side by `ConfigReplication`. Overrides for modules the sim reads (`LiveConfig.SimCritical`: `Combat`, `AimAssist`) are staged while a match runs and adopted at `MatchPreparing`, so combat constants never change underneath a running match. Pure rules live in `src/shared/Game/Config/` (`ConfigOverrides`, `ConfigRuntime`) and are spec-tested. See `docs/live-configs.md` for authoring and for adding a key. A config table holding a live leaf must not be `table.freeze`d.

## Testing

Headless specs live in `src/shared/Tests/*.spec.luau` and use `TestKit` (`toEqual`, `toBeNear`, `toBeTruthy`, `toBeNil`). `run-tests.luau` generates its sourcemap from the test-only `tests.project.json` and fails if generation fails or the suite is empty. Production projects exclude this tree and UI stories. The separate TestEZ suites in `src/tests/Shared` and `places/<place>/tests` remain under `ServerStorage.Tests` for in-place validation. `src/tests/Helpers/MockWorld.luau` is the shared AABB `WorldSnapshot` helper for both harnesses; it is server-only in production. Anything in `Sim/`, `Modes/`, `Economy/`, or `Quests/` is pure and must stay runnable headlessly — if new shared logic needs engine APIs, put that part in an adapter or service instead. Selene excludes `*.spec.luau`. Add or extend a spec whenever you touch pure logic.

## Conventions

- Luau with `--!strict` at the top of modules; tab indentation; StyLua-formatted (`stylua src places`).
- Services/modules are plain tables with functions; a `start()` guards against double-start with a `started` flag.
- Live admin command seams use `ForAdmin`; actual fixture/reset seams retain `ForTest` or `_resetForTest`. State subscriptions use `subscribe`; event streams retain `onEvent` and `onIntent`.
- Comments follow rule 1: module-top responsibility/invariant blocks, minimal inline.
- Selene (`std = "roblox"`) with `unused_variable` allowed.
